## 三、已退役／被否決

| 項目 | 原因 |
|---|---|
| E1、E2 文組標「X自然」（標多數人） | 與「標少數」原則衝突，使用者認為不合理 |
| 理組一律預設標「X社會」 | 應標「實際不考社會的人」，不是整個理組一律標 |
| 「最後一間教室吸收剩餘學生」當作獨立規則 | 使用者更正：每間教室都排滿，這只是排滿的結果 |
| 允許編號順序的手動例外（選項 2） | 使用者選硬規則 |
| 手動匯入匯出 JSON 取代資料夾授權 | 使用者用 Chrome，不需要 |
| 抽離自習維持手動統計、第一版不做 | 使用者決定一起做 |
| 修習「數 A 或數 B」另存欄位 | 組別已含考科，對座位與標籤沒有直接影響 |
| 座位併排（雙人桌）功能 | 使用者：模擬考是重要考試，沒有併排 |
| 與座位小幫手共用元件 | 使用者選擇不共用，避免兩個 repo 綁在一起 |
| 演算法算不出解時自動放寬規則 | 使用者選擇擋下並說明原因 |
| 單人特例釋出原教室座位 | 與「每間排滿」衝突 |
| 資料檔直接用 Excel | 格式容易被誤改，零錯誤較難保證 |
| 排座結果不存檔、每次重算 | 程式升級後舊模擬考座位可能變動，不利事後查註 |
| 設計稿與正式程式「完全共用互動程式碼」 | 選 TypeScript + Preact 後，只有樣式與標籤結構可沿用 |

## 四、未決議題

1. **排座演算法的實際對錯**：D24 草案尚未用 8 張舊座位表驗證，這是施工前的第一項驗證，也是最大風險。
2. **字型**：舊成果用華康特粗明體與華康正顏楷體 W5。PDF 取決於列印那台電腦的字型，Word 取決於開檔那台電腦的字型；是否內嵌字型或提供替代字型尚未討論。
3. **頁面流程的細節**：D20 只定骨架，各步驟的畫面與操作由使用者之後補充，設計員提案時再逐項討論。
4. **個別覆寫的畫面操作細節**（D26 定了行為，沒定畫面）。
5. **六步驟工作區是否允許隨時跳步**，以及「過期」標示的呈現方式。
6. **座位小幫手的設計規範位置**：它是否有 `docs/design/`、設計 tokens 在哪，設計員開工時要先查證；本次只看過畫面。
7. 技術選型的細節：Preact 的狀態管理方式、測試框架（建議 Vitest）、Excel 解析套件（建議 SheetJS 並打包進專案）。施工前由調度員與施工員確認。

## 五、驗證策略（我方建議，尚待實作）

- 排座後由**獨立驗證器**逐項檢查，任何一項不過就不許匯出：人數等於座位數、每人恰坐一個位置、空位未使用、深位同班連續、班級不穿插、文理不混、同班編號遞增。
- 既有的座位表當「黃金測試」：用同樣的名單與教室設定重排，結果必須通過同一套驗證。**不要求與舊成果逐格相同**，因為舊成果含人工例外。
- 表頭人數、標籤注意事項全由程式計算，不手打。
- 因為要求零錯誤，排座演算法與驗證器實作時建議使用較強的模型與較高的思考強度。
